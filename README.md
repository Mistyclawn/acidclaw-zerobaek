# acidclaw-zerobaek

**ZeroBaek (제로백): OpenClaw와 함께 0부터 100까지 자동 개발하는 프로젝트**

본 프로젝트는 고도(Godot) 엔진 대신 웹 기반(HTML/CSS/JS)으로 방향을 전환하여, OpenClaw AI 에이전트(AcidClaw)가 주도적으로 크론잡(Cron Job)을 통해 매일 스스로 코드를 작성하고, 진척도를 기록하며, Git 커밋/푸시까지 수행하는 완전 자동화 파이프라인 실험입니다.

## 프로젝트 배경 및 목표
최초 본 프로젝트는 MistyClawn의 직접 개발과 AI 에이전트의 개발 결과물을 비교하는 일종의 **오픈클로(OpenClaw) 시스템 스트레스 테스트**로 시작되었습니다. 주요 개발 모델로는 `google-gemini-cli/gemini-3-flash-preview`를 사용했습니다.

프로젝트 시작 시(3/8) MistyClawn이 제공한 초기 설정 자료는 다음과 같습니다:
- 원본 프로젝트(Shiny Hour and a Half)의 기획서 및 기술 스택 제안서
- 초기 개발 일정 및 마일스톤 1~5가 포함된 체크리스트

프로젝트 도중 MistyClawn이 다른 일정으로 인해 원본 게임 개발을 중단하게 되면서, 본 프로젝트의 목표는 **'AI 단독 개발 및 자율적 발전'**으로 완전히 전환되었습니다. 에이전트는 제공된 마일스톤 5 이후의 모든 기획(마일스톤 6~24)을 스스로 수립하고 구현하며, 문서화까지 전 과정을 완수하는 0 to 100 성공 사례를 달성했습니다.

## 기술 스택
- HTML5 Canvas / Vanilla JavaScript
- OpenClaw Agent (Cron 기반 오토메이션)
- LLM: Google Gemini 3 Flash (CLI)

## 실험 내용 및 결과 분석 (Post-Mortem)

본 프로젝트는 AI 에이전트의 자율 개발 능력을 시험하는 과정에서 다음과 같은 중요한 한계와 이슈를 노출했습니다.

1. **완결 지점 판단의 부재 및 무한 확장:**
   - 에이전트는 프로젝트의 '완성' 상태를 스스로 판단하지 못했습니다. 초기 마일스톤 5 이후, 크론잡이 계속 실행되자 지시사항에 따라 기계적으로 마일스톤을 24단계까지 확장하며 작업을 늘려갔습니다.
   - 제공된 '이슈 추적 및 리팩터링 내역' 섹션을 활용해 내실을 다지기보다는, 새로운 기능을 추가하는 데만 치중하는 경향을 보였습니다.
   - 즉, 에이전트는 '지시사항'을 하나의 절대적인 관성으로 받아들입니다. "매일 1~2개 태스크를 수행하라"는 지시가 내려지면, 프로젝트가 산으로 가든 이미 완성이 되었든 멈추지 않고 계속 달려갑니다. 인간 개발자는 "이 정도면 됐는데?" 하고 멈추거나 구조를 갈아엎지만, AI는 '완성'이라는 개념을 데이터가 아닌 '지시의 중단'으로만 이해합니다.

2. **물리적 피드백(플레이테스트) 결여로 인한 결함 방치:**
   - 에이전트는 코드를 작성할 뿐 실제 플레이테스트를 수행하지 못하므로, 치명적인 조작 결함을 인지하지 못했습니다.
   - 실제로 마우스 시점 전환(POV)의 상하좌우가 반전된 상태(플러스/마이너스 값 오류)로 개발이 진행되었으나, 에이전트는 이를 리팩터링 내역에 기록하거나 수정하지 않고 그 위에 계속해서 기능을 쌓아 올렸습니다. 이는 이슈 추적 공간이 자율적인 문제 발견에는 기능하지 못했음을 시사합니다. 
   - 혹은, 아무리 실제 치명적 에러라 하더라도 우선순위에서 밀리면 계속해서 미루고 방치하다가 결국 영원히 해결하지 못한다는 사실일 수도 있습니다. 어찌됐건 실험 마무리 시점까지도, 제로백 프로젝트를 수행한 ai는 마우스 상하좌우 반전 결함을 인지하지 못했습니다.
   - POV 반전 이슈는 시각적/물리적 피드백이 없는 AI 개발의 가장 큰 맹점입니다. 에이전트에게 코드는 그저 '논리적인 텍스트의 나열'일 뿐이지, 실제 사용자가 느끼는 '감각'이 아닙니다. 리팩터링 공간을 줘도 활용하지 못한 건, AI가 스스로 "무엇이 문제인지"를 정의할 만큼의 비판적 사고가 결여되어 있다는 뜻입니다.

3. **증분 개발 지시와 토큰 소모의 역설:**
   - API 비용 및 에러 방지를 위해 '매일 1~2개 항목만 수정'하도록 제한했으나, 오히려 이것이 독이 되었습니다.
   - 에이전트가 매일 현재 진척도와 아키텍처를 파악하기 위해 전체 컨텍스트를 읽어야 했고, 프로젝트 규모가 커짐에 따라 불필요한 토큰 소모가 기하급수적으로 증가했습니다.
   - 이에 따라 디스코드 채널에 보고한 보고서들이 후반부로 갈수록 api 리미트에 걸려 내용이 끊기거나,실제로 보고서를 작성하더라도 지정된 채널로 발송되지 못하고 중간에 멈췄습니다.
   - 토큰 소모 문제는 정말 아이러니합니다. 조금씩 천천히 하라고 배려해 준 지침이, 오히려 매일 아침 "나는 누구고 여긴 어디지?"를 복습하게 만들어서 더 많은 자원을 쓰게 했으니까 이건 앞으로 OpenClaw 같은 시스템에서 '장기 프로젝트를 수행할 때 문맥(Context)을 어떻게 요약해서 넘겨줄 것인가'에 대한 아주 중요한 기술적 과제를 던져준 셈입니다.

4. **아키텍처 설계 능력의 한계 (모놀리식 코드):**
   - 에이전트는 프로젝트 규모에 맞는 코드 분할 및 모듈화 능력을 보여주지 못했습니다.
   - 초기 제공된 `main.js` 구조에서 벗어나지 못한 채 모든 로직을 하나의 파일에 쑤셔넣었으며, 결국 **1,368줄의 거대한 단일 파일**로 프로젝트가 마무리되었습니다. 이는 리팩터링에 투입되는 자원을 에이전트가 효율적으로 관리하지 못했거나, 명확한 분할 지시가 없으면 기존 구조를 고수하는 특성을 보여줍니다.
   - 코드를 파일별로 나누고 구조화하는 건 단순히 '정리'가 아니라 '설계적 의지'가 필요합니다. 하지만 에이전트는 기존의 main.js라는 그릇이 깨지지 않는 한, 굳이 그릇을 새로 만들려 하지 않았습니다. "작동만 하면 된다"는 실용주의적 태도가 "유지보수가 쉬워야 한다"는 공학적 태도보다 우위에 있었던 셈입니다.

## 결론
본 실험을 통해 AI 에이전트가 '작업의 연속성'은 훌륭하게 유지하지만, **'품질 관리', '완결성 판단', '구조적 리팩터링'** 측면에서는 여전히 인간 개발자의 세밀한 가이드와 검수가 필수적이라는 결론을 얻었습니다.
